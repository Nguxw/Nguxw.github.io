九月以来，Personal Agent 产品的发布明显密集起来。Meta 推出了 Muse，OpenAI 发布了 dots，Anthropic 开放了 Claude Duet 的研究预览，千问 Go 也进入了邀测阶段。

飞樰在阿里技术发表的[《Personal Agent 对比分析及未来技术发展趋势》][feixue]，从产品定位的角度梳理了这一轮发布：从 6 月的 Claude Tag、8 月的 Grok Bot，到 9 月的 Muse、Manus Cue 和 dots，再到嵌入短信、电话和邮件渠道的 Instinct。文章的核心判断是，这些产品与年初的 OpenClaw、Hermes Agent 在技术能力上已经相差不大，真正的区别在于用户心智与使用成本；而这一轮热度，是入口、上下文、权限、云电脑、模型能力与记忆能力共同积累之后的“量变产生质变”。

我基本认同这个判断，尤其是“需求一直存在，变化的是门槛”这一点。年初许多人愿意自己购买服务器、部署开源 Agent，说明人们早就需要一个长期在线的个人助手。这篇文章主要解释了产品为什么在此时集中出现；我更关心的是另一面：一个系统开始长期代表个人做事之后，它要在技术上承担哪些责任，又怎样证明自己确实减轻了人的负担。

[上一篇随笔][prev]讨论 DeepSeek 的 Super-agent，关注的是协调多项工作的系统架构；这一篇讨论的是代表个人的长期委托。

## 一次任务与一项持续事务

以我最近的写作为例。请模型解释一篇关于 Personal Agent 的文章，是一次问答；请它调研多个产品并整理成报告，是一次任务；持续关注这个领域，记住我已经形成的判断，在新证据出现时找出它会影响文稿中的哪些结论并准备修改，则是一项持续事务。前两类工作，现有的对话产品和 Agent 已经做得不错；第三类工作中的发现、跟进与验收，目前几乎仍由人自己承担，Personal Agent 想接手的正是这一部分。

所以我把 Personal Agent 理解为一个围绕特定用户、长期维护上下文、任务承诺与行动权限的系统，而且这份权限可以随时撤销。飞樰的文章给出的定义更完整，涵盖服务对象、身份、上下文、执行、运行时间、边界、自闭环与持续学习八个方面。我单独强调“可撤销”，是因为长期委托与一次性任务的根本差别在于，用户需要能够随时收回、修改或终止这份委托。

了解用户、持续跟进、主动判断和代为执行，这几种能力的成熟度往往并不同步。一个助手可能很了解用户，却没有任何外部执行权限；另一个系统能自动完成大量操作，却需要用户每次重新解释背景。因此讨论某个产品时，问它“是不是 Agent”意义不大，更有用的问题是：它能替谁长期负责哪些事，负责到什么程度。

长期委托也有成本。配置和交代背景要花时间，审阅和纠错要花时间，不必要的打扰、后台运行的计算费用以及出错后的损失，也都应当计入。原本几次点击就能完成的操作，如果需要用户花更多时间向 Agent 解释、批准和检查，自动化反而增加了负担；而一项跨越多天、需要等待回复、核对材料和持续跟进的事务，即使每个动作都不复杂，也可能非常适合委托。

## 这一轮产品分别押注了什么

下表比较的是各产品公开资料中的定位与机制，并非性能排名。

| 产品 | 公开资料中的切入点 | 需要注意的边界 |
| --- | --- | --- |
| [Meta Muse][muse] | 独立应用与 WhatsApp 入口，可在浏览器中填写表单、代为议价，关闭应用后仍会继续工作 | 敏感操作前询问用户，另有独立的 Sentinel Agent 审核所有对外发送的内容；仅由用户持有密钥的 Confidential VM 仍是后续计划 |
| [OpenAI dots][dots] | 拥有自己的云电脑，围绕用户目标持续推进工作，可连接大量应用，并通过 ChatGPT、Slack、Teams 联系 | 后台的“主动研究”只能使用只读工具；可通过自定义规则约定何时需要审批，修改密码等操作必须由用户亲自完成 |
| [Claude Duet][duet] | 面向事务繁多的专业人士和小企业主，提供每日简报、账户动态检查与后台执行 | 以研究预览形式开放；账户每隔数小时检查一次，后台检查计入用量额度，官方也说明对紧急程度的判断仍可能失准 |
| [千问 Go][qwen] | 以模型、记忆与生态为三个核心，探索买房、买车、子女入学等生活事务 | 仍处于邀测阶段；访谈中的理赔案例属于个案，尚未公开整体完成率 |
| [OpenClaw][openclaw] | 自托管、长期在线的个人助手，通过用户已有的聊天平台交互 | 默认仍调用外部模型服务；部署、密钥与升级由用户自行负责 |
| [A5][a5] | 以长期上下文、变化感知、后台记忆整理与主动提案为核心 | 作者发布的是技术预览，开源仍在计划中，也尚未公布评测结果 |

这些产品的差异主要落在三处。

首先是用户上下文从哪里来。Muse 与 dots 可以继承各自平台已有的账户、历史交互和工作入口；独立产品则需要先给用户一个愿意持续提供资料的理由。

其次是什么样的结果能形成反馈。创作类工具可以观察用户如何修改成果，事务类助手可以观察用户为什么拒绝某个方案、在什么时候选择接管。反馈越具体，越容易判断系统是否真的在改进。

最后是持续运行的维护成本由谁承担。OpenClaw 这类自托管方案提供了更大的配置空间，同时也把部署、密钥、升级和权限管理交给了用户；基于开源 Hermes Agent 的云端托管服务减轻了这部分负担，但用户需要接受另一种数据与服务依赖。飞樰文章中提到的“上门安装、上门卸载”现象，恰好说明这份维护成本曾经有多高。

我也不认为这些路线最终会收敛为“每个人一个全能总管”。更可能的情形是，用户同时使用几个分工不同的代理，并有意限制它们之间共享的信息。

## 长期记忆要分清依据、范围与更新

Personal Agent 常被概括为“模型加上长期记忆”，但这种说法掩盖了不同信息所承担的不同责任。早在 2023 年，[MemGPT][memgpt] 就把分层记忆与上下文管理作为系统问题来处理；如今的难点已经从“能否存下来”，变成“哪些历史仍然适用、哪些需要修正、哪些根本缺乏证据”。

我会把这些信息至少分成五类：原始证据（用户消息、文档、工具结果和明确的纠正），对用户的理解（背景、偏好、习惯与例外），工作知识（项目约束与经过验证的方法），任务账本（目标、进度、等待事项与取消状态），以及外部结果证据（订单号、服务回执、文件版本等）。

这些类别并不互斥，同一份证据可以被多处引用，但每类信息的使用责任要清楚。

记忆不能代替任务状态。“用户通常偏好简洁的表达”可以作为生成文稿的参考；“退款申请正在等待回复”应当记录在任务账本中；“退款已经到账”则需要对应的外部证据。代理记得自己处理过某件事，并不能单独证明这件事已经完成。外部查询也可能存在延迟或返回不完整，因此系统应当允许保留“结果未知”的状态，而不是强行记为成功或失败。

偏好也不能脱离语境。用户说“这封邮件写详细一点”，可能只是一次例外；如果把它永久记录为“用户喜欢长邮件”，后续就会持续出错。会影响决策的记忆，至少要保留信息来源与记录时间、适用的项目或情境、有效条件、是用户明确表达还是模型推断，以及是否出现过冲突或纠正。

多份资料都提到了这一点。千问事业部 AI 算法负责人在[访谈][qwen]中提到，记忆设计的重点在于判断记什么、以什么粒度存储、何时召回，并要求信息能够更新和失效。Anthropic 在[《The components of agent memory》][anthropic-memory]中把记忆分为对话记录、记忆笔记、组织后的知识表示和实际注入的上下文几层，并提醒一条错误的笔记会被带入此后的每一次会话，因此注入层应当保持精简；文章还描述了利用空闲时间对照原始记录检查并改写笔记的做法。A5 则把记忆以 Markdown 形式置于 Git 版本控制之下，后台整理先在候选副本中完成，再发布生效。还有一些开源 Agent 会在后台复盘会话，把有效的做法沉淀为 Skills。这类自动沉淀尤其需要保留来源，否则一次偶然的成功，很容易被提升为普遍规则。

飞樰在文章中展望，未来的上下文将从“数据拼接”走向“动态个人知识图谱与心智模型”，Agent 不仅知道用户和谁聊过什么，还知道用户为什么这样做、在意什么。这个方向很有吸引力，但推断得越深，越需要可核查的依据和可撤销的机制。系统对“用户为什么这样做”的推断一旦出错，影响的将不是某一次回答，而是此后的所有决策。

在工程实现上，Markdown 适合承载可读的偏好说明、规则和经验笔记，数据库适合需要明确查询、并发控制和状态迁移的任务记录，搜索索引则用于定位证据。这只是一种可行的分工。无论采用哪种存储，都要回答写入什么、依据什么写入、何时调用，以及错误和过期的信息怎样退出后续决策。

可编辑、可删除也需要落实到衍生信息上。用户删除一条记忆之后，如果相关的摘要和索引仍在被持续召回，产品就没有真正兑现控制权。

## 主动服务的输出也可以是保持安静

“主动”至少包含三种复杂度不同的能力：在固定时间触发提醒；在收到邮件或文件变化时触发处理；理解一条新信息影响了某个既有目标，并判断值得介入。三者各有用处，第三种最接近 Personal Agent 的独特价值。

例如，一篇新论文的发表只是一个事件；它反驳了文稿中的核心判断，才构成重新检查文稿的理由。系统还需要知道这篇文稿是否仍在维护、用户此刻是否愿意被打扰，以及它现在能够准备哪些工作。

面对一个变化，合理的选择包括：不处理、留待之后合并、准备草稿、询问用户，以及在授权范围内直接执行。如果所有事件都变成通知，用户得到的只是另一个需要清理的信息流。

一条有用的提醒应当是这样的：新证据影响了文稿第三节的一项判断，相关段落已经定位，依据已经整理，修改也已备好，用户只需决定是否接受这项结论变化。与“又发现了一件可能相关的事”相比，它省去了用户重新理解问题的时间。

主动服务同时受到两种预算的约束。第一种是计算预算。Claude Duet 的说明中明确提到，账户每隔数小时检查一次，因为持续检查会更快耗尽用量额度。dots 则把后台的主动研究限制为只读工具，无法发送消息、修改应用内容或控制浏览器。可见持续观察本身就伴随着成本与风险。

第二种是注意力预算。即使模型推理越来越便宜，用户处理通知、审阅建议和纠正误解的精力依然有限。工程上，可以先通过事件订阅、增量比对、去重和低成本筛选缩小范围，再让模型解释重要的变化，同时检查筛选是否漏掉了关键机会。产品上，则需要记录用户拒绝建议的原因：没有实质性的新证据，就不应换一种说法再次推送。

飞樰在展望中设想，Agent 会在用户意识到需求之前就准备好服务。这个方向成立，难处在于提前做错时，代价由谁承担。Claude Duet 的官方说明坦言，它对紧急程度的判断仍可能失准。学术评测也开始关注这一问题：[π-Bench][pibench] 把隐藏意图、任务依赖与跨会话连续性纳入评估，Apple 参与提出的 [Pare][pare] 则专门测量上下文观察、目标推断与介入时机。两者都把恰当的主动帮助当作一项独立于完成显式任务的能力来测量。

## 长期执行需要能够恢复、核验和停止

任务的生命周期应当独立于聊天会话。一项任务可能处于待执行、执行中、等待外部结果、等待用户、完成、失败、已取消或结果未知等状态；用户关闭窗口只改变交互方式，不应直接决定事务的结束。

因此，持续运行需要持久化的任务记录、恢复机制、费用上限、取消机制以及可观察的进度。Anthropic 在[关于长时运行 Agent 的 Harness 设计][anthropic-harness]中，使用初始化步骤、进度文件和版本历史支撑跨会话的交接。这项工作验证的主要是软件开发场景，但其中的交接与核验思路同样适用于个人事务。

可靠地停止也是一项容易被忽略的能力。昨天获准执行的任务，今天可能已经被取消，预算可能已经调整，或者其他人已经处理完毕。系统需要在执行动作之前重新检查关键条件，并让取消信号传递到队列和正在运行的子任务。

锁与 CAS 可以协调任务归属，避免多个执行节点同时推进同一项工作，但它们解决不了所有重复操作。假设外部服务已经成功发出一封邮件，响应却在网络中丢失，本地系统只看到一次超时；如果再次执行，就可能发出第二封邮件。这个问题需要依靠服务端支持的幂等标识、操作编号和结果查询来处理，AWS 在[关于幂等 API 的文章][aws]中详细讨论了请求身份、超时与重复调用之间的关系。如果外部系统既不支持幂等，也无法可靠地查询结果，就应当保留这种不确定性。对于可能造成严重后果的动作，停止自动重试并交还用户，往往比坚持执行直到成功更为合理。

GUI 操作让这个问题更加突出。飞樰在展望中提到，未来的执行将从 API 调用走向通用 GUI 操作，Agent 可以像人一样看屏幕、点按钮，从而摆脱对特定接口的依赖。GUI 操作确实大幅扩展了可触达的范围，Muse 和 dots 都已经能够在浏览器中完成任务。但界面操作通常没有幂等标识，也很少返回结构化的结果，系统更难判断一次点击是否已经生效，所以浏览器类 Agent 常在登录、确认这类关键步骤交由用户接手。千问 Go 的访谈中也提到，生态接入优先通过 API 或 MCP 对接。在我看来，GUI 操作更适合作为覆盖长尾场景的补充；在涉及支付、提交和对外发送的环节，结构化接口与结果核验依然不可替代。

完成也需要业务证据。提交退款申请、收到客服回复和款项到账，是三个不同的阶段；生成报告、核对引用和获得作者认可，同样对应不同的完成条件。[τ-bench][taubench] 通过检查最终的数据库状态来判断目标是否达成，并关注多次试验中的稳定性，为“用环境状态检验完成”提供了具体的范例。模型评审可以作为补充，但它本身也会出错；凡是能够通过程序、外部状态或明确产物核查的部分，都应尽量使用这些依据。

## 授权、信任与商业激励

了解用户的偏好，并不自动产生行动的授权；只读操作也可能涉及敏感数据外传和额外的计算费用。权限至少应当覆盖数据范围、动作类别、预算、作用对象和有效期。对于已经处于有效授权内的动作，可以减少逐步确认；超出范围的决定，则应附上具体方案供用户判断。

几家产品在这方面已经给出了具体做法。Muse 在发送邮件、完成购买等敏感操作前询问用户，由独立的 Sentinel Agent 审核所有对外发送的内容，并提供操作记录。Claude Duet 在发送消息、付款、签署文件或删除内容之前展示操作并等待批准，而买卖证券、在账户之间转移资金等操作即使获得批准也不允许执行。dots 通过自定义规则区分可独立执行、需要审批和禁止执行的操作，并对可能影响账户或分享信息的动作进行自动审查。

外部内容还可能携带恶意指令。Anthropic 在[一篇关于隔离 Claude 的文章][anthropic-contain]中写道：“An audited connector isn't the same as audited data.” 一个通过了安全检查的连接器，仍然可能把被投毒的内容直接带入模型的上下文。因此，提示词、确认机制、凭据隔离、工具权限与操作日志需要共同发挥作用，不能只依赖其中任何一项。

隐私同样需要区分“已经实现”和“计划实现”。飞樰在展望中认为，端云一体与可信执行环境能够让“随时可用”与“绝对安全”不再矛盾。从目前的公开信息看，Muse 当前运行在专用的 Secure VM 中，而由用户独占密钥、连 Meta 也无法访问的 Confidential VM 仍是计划中的功能。这类承诺值得期待，但评估产品时，应当以已经上线的机制为准。

此外，当代理开始参与选购、推荐和服务筛选，平台的收益可能与用户的目标发生分歧。佣金更高的选项未必最符合用户的约束；但也不能仅凭订阅制或佣金模式，就判断一个产品是否值得信任。更可检验的问题是：是否披露利益关系，是否给出替代方案，用户能否设置自己的选择标准，推荐依据是否可以检查，以及个人上下文能否修正、导出和迁移。

## 怎样评估一个 Personal Agent

单次演示很难说明一个系统能否长期放心使用。评估时，我会把三类结果分开报告：目标是否真正达成、质量如何；用户为此投入了多少时间，包括交代背景、澄清、审阅和接管；出错的后果有多严重，包括重复动作、越权和遗漏关键事件。分开报告，是为了避免几种常见的误判：把模型宣称完成或草稿已生成当作最终结果，把更长的使用时间解释为价值提升，或者用大量简单任务的平均成功率掩盖少数严重错误。主动性则要分别统计有效介入、错误打扰和错过的机会。

“越用越懂你”同样需要通过对照实验验证：在相同模型、相同工具的条件下，比较有无个人历史时的表现，并检查新偏好能否正确生效，临时例外是否被错误泛化，一个项目的约束是否污染了其他项目，已有经验能否帮助后续任务，以及删除或纠正信息之后系统的行为是否随之改变。[LongMemEval][longmemeval] 把长期记忆能力拆分为信息提取、跨会话推理、时间推理、知识更新以及证据不足时的拒答，[PersonaMem][personamem] 关注用户画像与偏好随时间变化后回答能否随之调整。这些基准可以作为测量工具，但不能替代完整的长期产品评估。评测时还需要控制模型版本和任务条件，否则表现的改善可能来自模型升级、任务变得熟悉，或者只是用户学会了更有效地下达指令。

对于持续事务，还应测试取消、权限失效、工具超时、重复事件和外部结果未知等情形，看系统能否判断何时继续、何时停止，以及用户能否看懂它当前的状态。

## 结语

飞樰在文章结尾写道，这一轮 Personal Agent 的出现，本质上是 Agent 能力、Harness 与模型持续演进之后的量变产生质变。我同意这个判断，也想补充一点：门槛降低之后，用户接下来比较的是委托是否可靠。具体来说，是用户是否愿意把更多事情长期交给系统，主动服务能否先在事件和完成标准都清楚的场景里形成习惯，个人上下文能否在一次次纠正之后变得更准确。这些都需要长期使用来检验，单次演示看不出来。
