Agent 承担了大部分代码编写之后，工程团队的瓶颈转移到了审查环节。Claude Code 与 Claude Cowork 的工程负责人 Fiona Fung 在今年 6 月的[一次演讲][fung]中谈到，写代码不再是限制团队速度的因素，取而代之的是验证、代码审查与安全。

10 月 15 日，Addy Osmani、Morgan Westlee Lunt 与 Qing Wang 发表了[《How the Claude Code team does code review》][article]，较为完整地公开了 Claude Code 团队处理这一问题的方式。文章给出的背景是：Claude Code 自身约 90% 的代码由 Claude 编写；6 月至 9 月，合并的 PR 数量增加了一倍以上，被回滚的比例下降了 40% 以上；Anthropic 的单体仓库每天合入的改动，从 5 月的约 2,500 个增加到 9 月的 3 万个以上。

这篇随笔梳理该文的主要做法，对照 Claude Code 的公开文档核对其中容易混淆的细节，并讨论哪些部分可以被规模更小的团队和个人项目借鉴。[前两篇随笔][prev]关注的是 Agent 怎样长期承担工作，这一篇关注的是 Agent 交回的工作怎样被检验。

## 被优化的量是人工时间

文章开头区分了代码审查的两项职责：在上线之前发现并修复问题，以及在团队内部建立对代码库的共同理解。全文主要讨论前者，后者留到接近结尾处单独交代。

在 AI 审查的覆盖面和深度达到要求之后，团队把优化目标定为：在回滚和事故不增加的前提下，使人工审查时间降到最低。与之对应的目标状态是，Claude Code 各仓库中的大多数 PR 在合并时至多有一个人参与，而这个人可以是作者本人。

为此，团队跟踪三项与人工时间有关的指标：每个 PR 的人工批准数（中位数与第 95 百分位）、人工评论数，以及 PR 等待人处理的时长。回滚率与事故率作为护栏指标同时观察。文章对护栏的解释很直接：如果这两项上升，人工时间并没有被节省，只是从审查阶段转移到了事后的排障与修复。

这一设定改变了衡量审查的方式。传统流程默认“每个改动都有人读过”即为合格；在这套做法里，人是否读过一段代码不再是目标，改动上线之后是否出问题、出了问题之后花了多少人力才是。流程中的每一层检查，都要以这个结果来衡量它是否值得保留。

## 一次改动经过的检查

文章按时间顺序描述了一次改动的经历，可以归纳为提交之前、每个 PR、批准与合并、合并之后四个阶段。

<figure>
  <a href="images/code-review/pipeline.svg"><img src="images/code-review/pipeline.svg" alt="示意图：改动在提交前先由 Agent 自行验证，并由新上下文的第二个 Agent 审查；每个 PR 经过必需 CI、AI 审查与安全审查；随后按风险等级决定人工批准数，进入合并队列，经功能开关与分阶段发布上线；线上事故被整理为评测集，并沉淀为规则。" width="960" height="540" loading="lazy"></a>
  <figcaption>图 1　一次改动在合并前后经过的检查（依据原文整理）</figcaption>
</figure>

提交 PR 之前，Claude 先运行测试、构建和 lint，并由第二个 Agent 在全新的上下文中审查 diff。文章强调要给 Claude 可以运行的检查，例如测试、构建或界面截图，并要求它展示输出。Boris Cherny 估计，具备验证手段可以使结果好上两到三倍；这是他个人的估计，文章没有给出测量方法。

这一阶段依赖两份文件。`CLAUDE.md` 说明技术栈、约定、目标与非目标，篇幅保持简短，细节指向其他文档。`REVIEW.md` 由代码负责人编写，文章认为写得好的 `REVIEW.md` 会说明在这个仓库里“失败”具体是什么样子，例如文档仓库的失败是内容与事实不符，配置仓库的失败是请求被路由到错误的位置；此外还会限制琐碎意见的数量，列出可以跳过的路径，并要求每条发现附上文件与行号。

每个 PR 都会经过 AI 审查。审查读取的范围是整个仓库与改动声明的意图，而不只是 diff；对于修复缺陷的改动，还会检查它是否触及根因。多个 Agent 并行查找问题，另一组 Agent 对每条发现投票，只有获得足够认同的发现才会发布，纯风格和清理类的意见被过滤。发布的评论分为 Important、Nit 与 Pre-existing 三类，每一条都必须被答复：要么修复，要么说明理由后关闭。文章提到，在研究预览上线时，内部 PR 中获得实质性审查意见的比例从 16% 上升到 54%；超过 1,000 行的 PR 大多会被发现问题，小的 PR 则多数没有发现。

未处理的缺陷发现和安全发现会阻止合并。lint、类型检查、各平台的测试与构建同样是必须通过的检查。PR 模板要求写明怎样测试、怎样撤销。

人工批准的数量按风险分级：

| 风险 | 示例 | 人工批准 |
| --- | --- | --- |
| 低 | 文档、文案、仅内部可见的功能、开关保护下的新增改动 | 自动检查与安全检查通过后不需要 |
| 中 | 一般的产品改动；缓存、自动更新器、系统提示词等敏感区域 | 一人 |
| 高 | 风险最高的代码，以及规定必须两人审查的路径 | 两人 |

分级有几条配套规则。等级由改动本身决定，与作者是谁无关：一个分类器负责判定等级，另一个分类器再判断是否仍然需要人参与；负责人列出的敏感路径和所有 CI 工作流文件始终需要人审查。较宽松的路径只对受信任的作者开放，主要是负责该代码的团队成员。一次批准只对应一个具体的提交，新的提交会使之前的批准失效。还有一条规则原文写得很干脆：“An agent's approval never counts as a person's.”

合并队列会把改动应用到最新的主干上重新运行检查，避免两个各自通过的 PR 合在一起破坏主干。合并之后，新功能通过功能开关先对 Anthropic 员工开放，发布渠道也分先后。出现问题时可以直接关闭开关，不需要重新部署。团队实行每周轮换的值班，事故复盘时要回答的问题是：哪一层检查本应发现它。

文章也承认了一处尚未补上的缺口：目前还没有在回滚或事故指标异常时自动收紧审批要求的熔断机制。

## 审查器本身怎样被检验

把审查交给模型之后，审查器的质量就成为需要单独测量的对象。文章在这一部分给出的做法，比流程本身更有参考价值。

第一项是把事故变成评测集。曾经引发事故或被回滚的 PR，经熟悉相关代码的工程师确认后进入评测集，审查器每天都会在这个集合上运行。提示词、工具或模型的任何调整，都要在全部用例上重新评分；分数没有提高，调整就不保留。

第二项是测量噪声。团队按作者的反应给评论分类：被修复、判断有误、属于有意为之，或者无关紧要。审查器还会在已知没有问题的 PR 上运行，用来统计有害的误报。团队写下的优先级是先发现真实的缺陷，再减少审查轮次。

第三项是收敛。文章讲了一个例子：某个 CLI 的 PR 在作者 Agent 与审查 Agent 之间一夜往返了五十多轮。对审查器反复标出的代码执行 `git blame` 后发现，约 59% 在第一轮审查时就已经存在。也就是说，后续轮次发现的多数是此前就有的问题，并不是修复过程中新引入的缺陷。

<figure>
  <a href="images/code-review/convergence.svg"><img src="images/code-review/convergence.svg" alt="示意图：作者 Agent 与审查 Agent 之间不加约束的往返可能持续几十轮；加入三轮上限、只审增量、按类别报告、不重复已发布的发现和夜间扫描之后，一轮通过的比例从 65% 升至 78%，需要五轮以上的比例从 8.9% 降至 1.5%，平均审查次数从 2.08 降至 1.32。" width="960" height="560" loading="lazy"></a>
  <figcaption>图 2　审查循环的收敛措施与前后数据</figcaption>
</figure>

团队为此采取了几项措施：设置轮次上限，三轮之后由审查器请作者重新考虑方案；前几轮之后只审查新增的 diff；按缺陷的类别报告，使同类问题一次修完；已经发布过的发现不再重复提出；既有代码中的问题交给夜间运行的审查 Agent 处理。据文章给出的数据，经过一轮审查与修复即通过的比例从 65% 上升到 78%，需要五轮及以上的比例从 8.9% 下降到 1.5%，通过所需的平均审查次数从 2.08 下降到 1.32。

这个例子说明，两个 Agent 之间的循环次数并不能代表审查质量。人类作者面对十条琐碎意见会权衡哪些值得处理，Agent 作者则倾向于逐条执行；如果其中一部分是误报，执行本身就可能引入新的问题。Claude Code 的[最佳实践文档][bp]里有相近的提醒：被要求找问题的审查者总能找出一些东西，如果每一条都照改，代码里会多出不必要的抽象层和针对不可能情形的测试。因此文档建议在审查提示中明确写上跳过风格问题。

用事故构建评测集时，有一个细节容易出错。评测要回答的是“审查器面对当时的代码，能否发现这个缺陷”，所以输入应当是缺陷引入时的改动与上下文，后来的修复提交和复盘结论只能留给评分一侧使用。Anthropic 在[《Demystifying evals for AI agents》][evals]中把评测对象区分为 transcript 与 outcome，前者是一次运行的完整记录，后者是运行结束时环境中的最终状态，并建议在可能的情况下优先使用确定性的评分方式。这一区分同样适用于审查器：它在评论中说了什么，与它是否使缺陷在合并前被修复，是两件需要分别检验的事情。

## 文章与产品文档的对照

文章描述的是 Anthropic 内部的流程，其中一部分依赖团队自己的仓库配置和内部工具。想借鉴这套做法的读者，使用的是公开的 Claude Code 产品，两者之间有几处差别，需要对照文档核对。以下内容依据 2026 年 11 月 15 日查阅的官方文档。

第一处是 `REVIEW.md` 的适用范围。文章在落地清单中同时推荐了本地运行 `/code-review` 和维护 `REVIEW.md`，容易让人以为本地审查也会读取这个文件。[本地审查的文档][local]写明，`/code-review` 遵循的是 `CLAUDE.md`，并不读取 `REVIEW.md`；后者配置的是在 GitHub 上运行的托管 Code Review 服务。希望本地审查遵循的规则，应当写进 `CLAUDE.md`，或者编写自己的审查 Skill 与子 Agent。另外，本地命令默认只输出报告，加上 `--fix` 才会把发现应用到工作区。

第二处是“核验”的含义。[托管 Code Review 的文档][managed]把一次审查分为查找、核验、排序与发布四个阶段，其中核验阶段是对照代码检查候选发现，过滤误报。文档同时说明，审查通过阅读 diff 与周边代码完成，不构建也不运行代码。因此，一条经过核验的发现，意思是它与代码相符，并不表示有测试证明了它。运行层面的验证需要由 CI 和作者一侧的检查承担，这也是文章把“提交前验证”与“必需 CI”列为独立层次的原因。

第三处是阻断合并的责任。文档写明，托管审查不会批准也不会阻止 PR，它留下的检查项也不会以失败告终，是否合并由团队决定。文章中“未处理的发现会阻止合并”描述的是团队在自己仓库中的规定；文章没有说明这一规定通过什么方式实施，产品本身并不提供这种约束。需要强制执行的要求，应当落实在分支保护、CODEOWNERS 与必需检查上，文章的落地清单也是这样建议的。

还有一个与安全有关的细节：托管审查读取的 `REVIEW.md` 来自基准分支或默认分支，不会来自 PR 自身的改动。否则，一个 PR 就可以通过修改审查规则来放宽对自己的审查。

## 审查意见要落到不变量上

文章反复强调证据：`REVIEW.md` 要求发现附带文件与行号，人的职责之一是阅读测试输出、执行过的命令和截图。对于涉及状态与并发的改动，这一要求可以再具体一些，即审查应当围绕不变量展开。不变量是指无论并发、重试、取消和恢复以何种顺序发生都必须成立的约束。

以长任务的接管为例。Worker A 取得任务的租约并开始执行，随后因为暂停而未能续租；租约到期后，Worker B 接管任务并写入了新的进度；此时 A 恢复运行，提交它在暂停之前计算出的结果。如果写回时没有额外的检查，A 的旧结果会覆盖 B 的新进度。

<figure>
  <a href="images/code-review/lease.svg"><img src="images/code-review/lease.svg" alt="时序示意图：Worker A 取得租约后暂停，未能续租；租约过期，Worker B 接管并写入进度；A 恢复后提交暂停前的旧结果，存储比较执行资格后拒绝写入，A 随即停止推进。" width="960" height="540" loading="lazy"></a>
  <figcaption>图 3　租约过期之后，旧执行者的写入需要被拒绝</figcaption>
</figure>

这类问题不会因为代码里使用了分布式锁而消失。[Redis 关于分布式锁的文档][redis]说明，互斥的保证只在锁的有效期内成立；释放锁时必须校验持有者，否则一个执行超时的客户端可能删除另一个客户端已经取得的锁。文档还建议实现 fencing token，并提醒不要假设取得锁的进程只要还活着就仍然持有锁。

审查这样的改动时，看到“已加锁”并不足以得出结论，还需要确认几件事：接管之后执行资格怎样变化；写回状态时是否检查了当前执行者仍有资格；条件更新失败之后，程序是否确实停止了推进；完成、取消、续租等入口是否使用了相同的约束。还有一种情形单靠条件更新无法处理：如果 A 在写入被拒之前已经向外发出了通知，写入失败并不会撤回这条通知。状态写入与外部副作用需要分别考虑，后者要依靠幂等标识与结果查询。

对比两种审查意见可以看出差别。“这里可能存在并发问题”只是一个怀疑，作者既无法确认也无法反驳。有用的意见会写出触发条件、实际经过的代码路径、导致的错误结果以及验证方法，例如指出某个写回函数没有比较 token，并给出“暂停 A、让 B 接管、再恢复 A”的执行顺序作为复现步骤。给审查 Agent 下达任务时也是如此：要求它检查“任务被另一实例接管后，旧实例是否仍可能更新进度、提交完成状态或继续执行外部操作”，比要求它“找出潜在问题”更容易得到可以核查的结果。

独立审查的作用也有边界。[最佳实践文档][bp]的说法是，新的审查者之所以有帮助，是因为它没有看到实现时的推理过程；把同一项任务转交给子 Agent，本身并不会让答案变好。新上下文不等于没有上下文，审查者仍然需要需求、系统约束和相关代码。多个 Agent 投票可以过滤一部分误报，但如果它们都不知道某一条业务约束，就会一起漏掉违反这条约束的缺陷。投票结果一致，并不能当作相互独立的证据。

## 留给人的部分

文章列出了仍然由人承担的工作：决定一项改动是否应该做，包括方向、取舍与范围；审查计费、自动更新器、CI 工作流这类高风险代码；审查会被其他人沿用的架构；阅读证据；以及对结果负责。文章的表述是，无论代码由谁输入，每一个上线的改动都有一个人为它负责。Fiona Fung 在演讲中的说法与此一致：人的审查应当放在需要专业判断的位置，例如信任边界与安全敏感的代码，而信任与验证之间的平衡会随着模型的进步继续变化。

审查的第二项职责，即建立共同理解，团队没有为它设计正式流程。需要了解某一部分代码时，工程师让 Claude 针对这一部分生成讲解，几分钟即可得到，内容反映的是代码当前的状态；也有人会生成一个小的可视化页面。团队默认在公开的 Slack 频道中工作，彼此可以看到对方在做什么。由于 Agent 使开始一项工作的成本很低，有些工作并不应该合入，团队倾向于在讨论中尽早提出不同的方向，而不是等 PR 完成之后再否决。

“谁合入，谁负责”这条原则有它的前提。文章列出的条件包括：改动足够小，便于审查、调试和回滚；几乎所有改动都可以通过开关、回滚和分阶段发布撤销；影响范围越大的代码，配备的人和检查越多；遥测与内部的高强度使用能够较快暴露回归；事故复盘针对的是系统，不追究个人。

这些前提决定了这套做法的适用范围。把大多数 PR 的人工批准降到一人甚至零人，依赖的是合并之后的开关、分阶段发布、内部先行使用、值班与一步回滚。缺少这些条件的团队如果只借鉴减少人工批准这一项，风险会直接落到用户身上。文章的落地清单也是按这个顺序排列的：先在一个仓库上启用 AI 审查并调整数周，再逐步扩大范围；先写下风险分级，再放宽低风险改动的批准要求；合并之后的回滚手段和以事故构建的评测集，则与前面的各项并列。

阅读文中的数据时还需要注意两点。这些数字来自团队对自身流程的报告，没有对照组；同一时期模型、工具与团队规模都在变化，回滚率的下降不能完全归因于审查流程。此外，Claude Code 团队审查的是自己每天高强度使用的产品，回归能很快被内部使用者发现，这一条件并不是每个团队都具备。

## 结语

这篇文章最值得借鉴的地方，是它把审查当作一个需要测量的系统：对人工时间设定目标，以回滚和事故作为护栏，用历史事故检验审查器，并为 Agent 之间的循环设置终止条件。具体的层数、批准人数和工具可以因团队而异。对个人项目而言，可以先落实的是其中成本最低的几项：给 Agent 可以运行的检查，让一个没有看过实现过程的审查者读 diff，把关键的不变量写下来，并要求每条审查意见附带可以核查的依据。
