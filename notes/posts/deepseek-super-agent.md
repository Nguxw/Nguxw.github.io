最近在同时使用多个 Agent 窗口推进工作时，我越来越明显地感受到：模型一侧早已可以并行执行，真正的瓶颈在于人。每个窗口进行到哪一步，新的需求是否同步到位，交回的结果能否视为完成，这些信息都需要人自己记住并判断。

因此，DeepSeek Harness 团队发布 Super-agent 设计文章后，我做了比较仔细的阅读。它试图回答的正是这个问题：当 Agent 需要持续承担工作时，系统能否替人分担更多的协调、记忆与验收负担。

在展开之前，先说明本文采用的衡量标准：一个 Super-agent 是否有价值，取决于在质量与权限边界都得到保障的前提下，它能否让人以更少的介入，获得更多可以直接接受的成果。后文的讨论都围绕这一标准展开。

## 设计文章、研究原型与底座

这篇文章是 DeepSeek Harness 团队于 10 月 31 日发布的[《Super-agent 设计探索：迈向更自主的 Agent 系统》][wscn]。作者在开篇即说明，文章并非对 DeepSeek Harness 现有产品功能的介绍。

文章的核心设计包括以下几个方面：

- **协调层与执行层分离。** Router 常驻运行，负责承接所有面向人的交互并分派任务，本身不执行具体工作，文中甚至提到它可以不配备 Bash 工具。Worker 拥有相互隔离的上下文和完整的执行工具，不直接与人对话，只向 Router 汇报进展；Worker 内部还可以继续创建 Subagent。
- **事件驱动。** 外部事件以 Trigger 的形式进入系统，依次经过确定性代码和 LLM 两级过滤。PR、IM 话题等 Thread 可以被 Worker 订阅，后续事件直接送达对应的 Worker。
- **异步执行。** 以异步的 ReAct 循环取代阻塞式调用。据文章介绍，该机制已在 DeepSeek Harness 中实现，但尚未默认开启。
- **状态、计算与执行环境分离。** 会话状态存放在数据库中，Agent Loop 运行于无状态的云端容器，执行环境则保留在用户本地机器上，通过不保存会话状态的轻量守护进程连接。此外，系统还设有一个由定时消息驱动的 Watchdog 会话，用于监控基础设施故障以及 Worker 是否在实际推进。

阅读时需要区分三个对象：DeepSeek Harness 是底座，Super-agent 是文章提出的系统设计，[`dsh-superagent-prototype`][proto] 则是公开的研究原型。原型的 README 明确说明，它仅供参考，并非 DeepSeek 的正式产品，与内部版本及文章描述的实现均不完全一致，文章中的部分设计属于未来的发展方向。就目前而言，原型的定位较为具体：一个面向单个 GitHub 仓库的主动式编码 Agent，可选择接入飞书。

还需注意，这里的双层组织与通常所说的多 Agent 分工并不处于同一层次。Router 与 Worker 解决的是多项工作之间的协调问题，Worker 内部的 Subagent 解决的才是单项工作的拆分问题。

在我看来，这套设计的价值在于，它把任务与任务之间的衔接放到了架构设计的中心位置。至于它在真实工作中能否带来净收益，还取决于上下文、权限、成本与验收几个环节的具体实现。

## 社区讨论的主要分歧

围绕这次发布，我梳理了几组具有代表性的观点。

Elvis（@omarsar0）在 [X 上][elvis]总体持支持态度。他认为，若要让 Agent 跨任务持续工作，就需要协调与执行分离的架构，并将状态、计算和执行环境解耦；在此基础上，才能进一步实现事件触发、跨设备持续可用等能力。他同时指出，这一思路同样可以基于其他现有的 Harness 实现，并不限于 DeepSeek Harness。在评论中，有人提出了一个实际问题：Agent 如何判断一项任务已经完成？Elvis 认为这是一个好问题，并坦言自己基于规则和上下文感知的实现 “honestly, it is not perfect”。

冯若航的[文章][vonng]提出了最具体的批评。他承认，如果把问题限定为“在一个对话框里自动切分 Session、异步派发任务”，这一开源原型的工程设计相当扎实。但他的核心观点是：Session 可以隐藏，Context 却必须显式呈现。代码仓库、各台机器上的工作目录、规范文件、工具权限和历史决策，都是用户需要看到的边界。由一个全局入口去推测某条指令属于哪个工作现场，在复杂场景下很容易出错。他提出的替代方案是按工作上下文建立群组，使群组本身成为显式的上下文容器。

GitHub 讨论区中也已经出现了实现层面的探索。vicfei 在[一则讨论][vicfei]中围绕准入与授权模型展开，并分享了社区项目 dsh-super-agent。该项目独立于 DeepSeek Harness 运行，可将 claude、codex、opencode 等命令行 Agent 作为 Worker 使用。aaron-kaka 则[建议][aaron]后台报告先对用户可见，默认不额外唤醒 Router，作为多项目场景下降低打扰的一种策略；帖子同时说明，该方案尚未实现，也未经过通知链路的端到端测试。

综合来看，这些观点分别对应四个问题：协调能否自动化，工作边界能否清晰界定，行动是否经过授权，结果是否值得打扰用户。

这四个问题需要统筹考虑。如果只解决其中一个，成本往往只是转移到了别处。例如，将十个聊天窗口收拢到同一个入口，确实减少了界面切换；但如果用户随后需要花更多时间确认系统将某条指令归入了哪项任务、是否在错误的位置执行了操作，整体收益反而可能为负。

## 人的注意力是一项成本

评估一个 Agent 系统时，我倾向于首先明确用户最终需要的交付物。修复缺陷需要的是一个符合要求的改动，开展调研需要的是一份能够支撑决策的结论，内容创作需要的是一件可以发布的作品。生成过程中消耗了多少 token、调用了多少次工具，并不是用户关心的对象。

基于这一点，我会用如下方式粗略估算一个系统的价值：

> 净价值 = 被接受的成果价值 − 模型与工具成本 − 人工介入成本 − 错误与返工损失

这是一个分析框架，而非经过实验验证的公式。它的作用在于提醒：节省下来的执行时间，可能会在检查、澄清和补救环节重新消耗掉。

以一个简单的数字为例：假设系统每小时交付 20 项结果，每项需要人工检查 5 分钟，那么一个人每小时最多只能完成 12 项检查。即使完全不需要返工，待审队列也会以每小时 8 项的速度增长。

在这种情况下，继续增加 Worker 只会让队列增长得更快。需要改进的是验收环节本身：交付物附上关键依据，完成标准表述清晰，可以自动化的检查尽量自动化，低价值的通知尽量减少。

原型的[设计原则][philosophy]对这一点有相当深入的考虑。文档的第一句便是 “Take as little human attention as possible”：消息、提问、设置项和面板元素都被视为对人类注意力的消耗，每一项带来的价值都必须超过其消耗，否则就应当移除。

我认同这一方向，但认为还需要补充一个前提：低打扰不应以牺牲透明度为代价。执行中、等待外部条件、需要决策、执行失败、等待验收等状态应当得到区分，用户也应当能够随时接管。减少过程性通知有助于用户保持专注，但隐藏失败只会推迟问题被发现的时间。aaron-kaka 的提案体现了同样的思路：报告的持久保存、对用户可见以及写入会话上下文，并不需要在同一时刻完成。

因此，相比同时运行了多少个 Agent，我更关注另一项指标：在任务类型相同、质量要求相近的条件下，人每投入一小时，能够获得多少最终被接受的成果。

## 工作上下文需要显式化

冯若航对工作上下文的强调，我十分认同。不过，我并不认为单一入口必然导致边界模糊。

用户完全可以只与一个助手交互，同时清楚地了解每项工作隶属于哪个项目、在哪台机器上执行、拥有哪些权限、依据的是哪一版需求。这些信息可以呈现在任务卡片、项目视图和交付记录中。会话编号、上下文压缩次数、后台运行的 Worker 数量等信息，大多可以交由系统管理；而项目归属与执行权限直接影响用户的决策，应当始终保持可见。

同时也应客观地看待原文：设计文章在“开放问题”一节中，已将会话之后的交互形态（例如能否直接在 GitHub 等领域界面中协作、用户如何在任务中途介入），以及跨组织、跨实例的上下文边界列为有待解决的问题，并未主张单一的全局上下文适用于所有场景。

进一步推演可以发现，跨会话的连续工作真正需要的，是一份能够确认当前事实的任务状态。

设想这样一个场景：上午在聊天中确定采用方案 A，下午在代码评审中改为方案 B。此时 Worker 仍在按方案 A 执行，Router 的摘要已更新为方案 B，另一个评审 Agent 读取的则是上午的文档。三个会话都完整保留了历史记录，系统却仍可能沿着不同版本的目标行动。

  <figcaption>图 3　历史记录完整，目标却已分叉</figcaption>

在这种情况下，检索更多的聊天记录并不能消除冲突。系统需要明确：当前有效的是哪个决定，由谁做出，替代了哪个旧决定，哪些正在执行的工作因此失效。

我倾向于以任务对象作为衔接这些信息的核心，其中至少应包含目标、所属项目、授权范围、当前版本、执行状态和交付物。模型生成的摘要有助于理解，但关键状态必须能够追溯到原始决定或执行结果。在存储方式上，规范、计划和说明性内容适合以 Markdown 承载，需要并发更新的任务状态适合存入数据库，历史材料则可以借助检索索引定位，具体选择应服从更新、查询和纠错的需要。

例如，旧 Worker 依据第 3 版需求完成了工作，而此时任务已更新至第 4 版。系统应在接受结果或执行外部写入之前进行版本检查。版本检查可以防止过期结果覆盖最新状态，但第 3 版的产出是否仍有参考价值，仍需依靠语义层面的判断。

我在腾讯参与 Goal 长任务的设计与实现时，采用的也是类似的分工：由会话状态机、CAS 幂等控制和分布式锁保障并发推进与重启恢复等确定性环节，由独立的 Evaluator 判断任务是否完成。确定性约束与模型判断需要协同设计，二者缺一不可。

## 主动执行的前提：授权与收益

“无人提示，系统便自主开始工作”在演示中颇具吸引力，但在实际使用中，还需要回答几个问题：这项工作为什么值得做？允许推进到哪一步？在什么情况下应当停止？

接收到一条消息只意味着获得了输入，采取行动还需要明确的目的和授权。例如，反馈群中有人报告了一个问题，在事先允许的范围内，Agent 可以检索日志、尝试复现并起草修复方案，这些工作都是在为后续决策准备材料。但将改动合入主分支、发布服务或对外发送消息，则需要相应的明确权限，这类授权既可以事先建立，也可以在具体的决策节点上获取。我在 SmartCS 中采用的正是这种方式：涉及写入的操作在执行前挂起，待人工确认后再恢复，并在恢复时进行幂等去重，避免重复办理。

原型在这方面制定了具体的规则。根据其[授权文档][auth]，允许名单、规则以及绑定于任务的授权（文档中称为 Mandate）均由宿主程序负责执行；消息、评论和引用的文档仅作为决策输入，无法改变既有权限。系统推断出的主动任务默认处于 observe 模式，只进行评估和记录，评估结果为正面的候选会被记为 “would accept”；团队审查这些记录后，再决定是否切换为自动接受。用户明确提出的请求在任何模式下均可执行。

相比在提示词中写一句“请谨慎行动”，这已经是可以检验的系统规则。但需要注意的是，这份文档约束的是谁可以发起工作以及任务的范围，并未说明单个工具调用的权限如何控制。

在这一点上，有一篇解读文章的推论值得商榷。博客“覆手为雨”的[文章][lininn]认为：Router 不参与执行，因而不具备删除文件、修改数据库的权限，即便群聊中混入一条提示注入，最坏的结果也只是任务分派错误，而不至于造成删库。

这一推论遗漏了一个环节：Router 本身虽不执行工具，却可能将恶意内容转写为下发给 Worker 的指令。此外，设计文章中提到 Router“甚至可以不配备 Bash 工具”，而公开原型的[架构文档][arch]显示，主会话实际上拥有 `bash`、`read` 等工具，文档也明确指出“避免读取代码”只是一条提示规则，而非工具层面的限制。

因此，职责分离与权限隔离需要分别检验。委派任务时，授权范围应随任务一同传递；执行动作时，仍需逐一校验该动作是否处于允许范围之内。我在 Mini-Hermes 中采取了类似的措施：限制对敏感路径的访问，高风险命令需经用户确认，工具可在无网络的 Docker 环境中运行。

主动执行还涉及成本与收益的权衡。假设系统每天接收一千条消息，其中真正值得处理的可能只有少数几条；若对每条消息都展开调查，模型费用和无效产出将迅速累积。我会依据预期收益来决定主动的程度，综合考虑产生有价值结果的概率、可节省的等待时间、所需消耗的资源，以及误判可能造成的损失。成本较低的准备性工作可以适当放宽触发条件，而成本高、影响范围大的动作则需要更充分的依据。

observe 模式在这里还有一项实际价值：先积累一批“系统原本打算执行什么”的记录，评估误触发与漏触发的比例，再逐步扩大可委托的范围。系统的自主程度可以随着证据的积累逐步提高，而无需一次性放开所有动作。

## 存活、恢复与进展

分析长任务架构时，我会将以下三个问题分开考察：

| 问题 | 所需证据 | 仅凭这一项为何不足 |
| --- | --- | --- |
| 进程是否存活 | 心跳、健康检查 | 存活不代表任务在推进 |
| 任务能否恢复 | 检查点、持久化的状态与待执行副作用 | 无法确认外部动作是否已经生效 |
| 工作是否接近完成 | 测试结果、外部反馈、验收结论 | 需要依据领域定义完成标准 |

考虑这样一个典型场景：Agent 已在外部系统中成功创建了一个工单，但在返回结果时网络中断，重启后日志中只留下一条超时记录。此时若直接重试，很可能会创建第二个工单。检查点保存得再完整，也无法回答第一次请求是否已经生效，这需要依靠操作标识、幂等接口或结果查询来确认。在无法确认的情况下，系统应当保留这种不确定状态，再决定采用何种恢复方式。我在淘天负责预发交付自动化时处理的也是这类问题：流程中断后，首先确认哪些产物已经生成，可复用的直接复用，再继续推进后续步骤。

原型在工程层面已经处理了其中一部分问题。每条命令在同一个事务中修改状态，并将待执行的外部工作登记到持久化队列中，事务提交后才实际执行；对外消息统一经由 Outbox 发送并记录回执。这些设计缩小了部分故障窗口，但具体外部动作的去重与结果核对，仍取决于对应接口是否提供支持。

另一方面，一个运行正常的 Agent 也可能持续偏离目标：反复修改同一段代码，重复检索相似的资料，或不断扩充报告的篇幅，却始终没有解决原本的问题。设计文章中的 Watchdog 正是为发现此类停滞而设，但监控本身也依赖可靠的进展信号。相比工具调用次数和运行时长，我更关注失败的测试用例是否减少、阻塞条件是否解除、交付物是否满足新增的约束。

用于验收的 Agent 同样需要校准。Anthropic 在一篇[关于长时间应用开发的文章][anthropic-harness]中指出，即使将生成者与评价者分离，评价者本身仍是一个倾向于宽待 LLM 产出的 LLM。增加一个独立会话进行检查，固然提供了额外的把关机会，但并不等同于独立、可靠的证据。如果多个 Agent 接受了同一个错误前提，彼此的认可依然可能导向错误的结论。

因此，不同类型的任务需要采用不同的验收方式。编码任务应结合测试、实际运行与人工审查；调研文章需要检查引用能否支撑结论、是否覆盖了关键的反例；演示文稿还需评估版式、可读性以及与需求的匹配程度。我在淘天搭建研发评测基准时，同样以历史需求、代码变更和验收条件为依据，其实质是将“完成”定义为可以检验的条件。我认为这是 Agent 产品无法回避的一项投入，同时，系统也应当允许结果停留在“待确认”或“部分完成”的状态。

## Harness 与模型的协同演进

Harness 的进展容易引出一个过度的推论：只要工程设计足够完善，模型能力就不再重要。从现有材料来看，更有依据的结论是二者需要协同优化。

LangChain 在 2026 年 2 月发布的一项[实验][langchain]中，固定使用 `gpt-5.2-codex` 模型，仅调整 Harness，便将编码 Agent 在 Terminal Bench 2.0 上的成绩从 52.8% 提升至 66.5%。需要注意的是，实验同时调整了推理预算的分配方式（文中称为 “reasoning sandwich”），且未单独拆分这一调整的贡献，因此“模型不变”并不等同于“计算量不变”。这一结果说明系统设计是影响效果的重要变量，但不足以推导出它在所有场景下都比模型更为关键。

相反方向的例子同样具有参考价值。Anthropic 在[另一篇文章][anthropic-managed]中提到，Claude Sonnet 4.5 在接近上下文上限时会提前结束任务，团队因此在 Harness 中加入了上下文重置机制；而在换用 Claude Opus 4.5 之后，这一行为不再出现，原有的重置机制反而成了多余的负担。

如果模型仍会反复误解关键的业务约束，增加调度和重试只会产生更多需要纠正的结果。人的注意力能否成为主要瓶颈，前提在于单项任务本身已经达到足够的完成质量。基于此，我会将 Harness 中的设计分为两类：

- **弥补当前模型不足的策略**，例如特定的上下文重置、反复提醒以及特定的任务拆分方法。这类设计需要随着模型的迭代重新检验。
- **连接真实工作所必需的机制**，例如身份、授权、任务状态、执行环境、外部结果与交付记录。无论模型如何升级，这些需求都依然存在。

多 Agent 架构同样可以放在这一框架下评估。增加执行单元能够扩大并行探索的范围，但收益大小取决于任务能否有效拆分、各单元获得的证据是否互补，以及协调本身需要付出多少成本。

Anthropic 的[多 Agent 研究][anthropic-multi]中有一个颇具说服力的例子。在一项漏洞挖掘实验中，协调式的 Agent 集群消耗约 2700 万 token，发现了 266 个漏洞；独立运行的对照组消耗约 650 万 token，发现了 21 个。二者差距看似悬殊，但集群约有一半的发现位于对照组并未被要求搜索的目录之中。若仅统计相同的核心目录，两种方法每单位 token 的发现效率大致相当。

协作的价值毋庸置疑，但在比较不同方案时，必须同时考虑预算、搜索范围与交付质量。新增的 Agent 带来的究竟是更多有效探索，还是仅仅更多的计算消耗，需要通过实验加以区分。

DeepSeek 自身的初步实验也应在其适用范围内理解。该实验以一个“只消耗时间”的工具替代真实的编码工作，因此衡量的是调度与协作能力，而非任务执行本身。每轮实验包含约 300 条消息，其中约 20 条为实际的工作请求，每种方案各运行 5 次。结果显示，Super-agent 完成任务的 p50 为 12.4 分钟，p95 为 15.7 分钟，优于配备 Subagent 工具的单会话方案（在中性提示下，单会话方案的 p95 达到 29.5 分钟，且 5 次运行中均未调用 Subagent），代价是消耗了更多的读缓存 token。文章也说明，上述实验基于合成负载和简化环境，属于初步结果，不能直接换算为真实研发场景中质量或效率的提升。

我希望今后的评测能够分两个层次报告结果：一层衡量事件处理、路由与恢复是否正确，另一层衡量最终交付是否合格。第一层表现良好是第二层的必要条件，但无法替代第二层。

## 选型时的评估方法

这种系统形态有其适用范围。对于偶尔生成一段文字或执行一次脚本的需求，常驻协调层带来的状态管理与维护成本，通常难以获得相应的回报。只有当工作持续产生、需要跨多个入口追踪，且各项任务能够在一定程度上独立执行时，这种组织方式才更值得投入。

如果要在实际项目中进行选型，我会先固定一组同类任务与验收标准，再对完整流程进行比较，而不是依据单次成功的演示做出判断：

| 评估项 | 对应的问题 |
| --- | --- |
| 最终被接受的成果比例 | 产出中有多少真正符合要求 |
| 每项成果所需的人工时间 | 澄清、检查与返工是否抵消了节省的时间 |
| 从提出任务到验收通过的耗时 | 完整的交付周期是否得到缩短 |
| 全部尝试的模型、工具与运行费用 | 失败与重试的成本是否计入 |
| 需求变更、取消与断线后的表现 | 能否正确应对真实工作中的变化 |
| 错误通知与未经授权的动作 | 主动性是否超出了可接受的范围 |

其中，我最看重的指标是每个被接受结果的总成本：将成功、失败、重试、人工检查与返工的成本全部计入，再除以最终被接受的结果数量。进行比较时，任务类型与质量要求应当尽量接近，否则这一指标同样会失真。

这一视角也会影响对产品机会的判断。如果通用底座使调度、持久化与工具接入变得更加容易，应用开发者便可以将更多精力投入到业务问题本身：用户真正想要完成什么，哪些信息是可信的，哪些动作可以被授权，以及如何证明结果是有用的。同样是生成一份研究材料，内部知识整理、市场分析与学术阅读对来源、更新频率、引用规范和评价标准的要求可能截然不同。将它们接入同一个模型接口，并不会自动得到同样好用的产品。

我的判断是，通用 Harness 将推动一部分基础能力走向复用，而领域内的任务定义、数据接入、验收方法与交付体验，仍需要具体的产品持续打磨。这只是对竞争方向的一种推测，最终仍需由真实用户的使用与留存情况来检验。

对我自己而言，这也为后续的学习方向提供了参考：在持续深入理解模型与上下文工程的同时，也要扎实补充状态管理、异步执行、权限设计与评测等方面的能力。一个长时间自主运行的系统，最终需要对它所改变的外部世界负责。

回到 Super-agent 本身，我最期待看到的进展是：任务变更后能够正确调整，执行失败后能够可靠恢复，交付时能够提供充分的证据，并将有限的人类注意力留给真正需要人来判断的环节。只有在这些问题得到较好的解决之后，“同时运行多少个 Agent”才会成为一个有意义的规模问题。
